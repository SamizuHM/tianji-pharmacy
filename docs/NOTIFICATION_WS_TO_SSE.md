# 工单实时通知从 WebSocket 切换到 SSE 的说明

## 背景

本项目最初为工单实时通知实现了一套独立的 `WebSocket` 服务，目标是让工单处理人员在页面打开后实时收到：

- 新工单进入待办
- 工单分发或转派到目标部门
- 工单有新回复
- 工单关闭
- 待处理工单数量变化

最初方案在本地单进程环境下可以工作，但和当前实际部署方式不匹配：

- 对外入口是 `cloudflared -> web:3000`
- `qdrant`、`ml-service`、`web` 都走容器内通信
- 浏览器端不应再依赖额外公开端口

而旧的通知方案要求浏览器去连单独的 `:3001` 端口，这在当前部署模型下不闭合。

## 旧方案：独立 WebSocket 端口

### 实现方式

旧方案的核心思路是：

1. `web` 进程内部额外启动一个 `ws` 服务
2. 浏览器先请求 `/api/notifications/session`
3. 服务端返回 `wsUrl`
4. 前端通过 `new WebSocket(wsUrl)` 建立连接
5. 工单事件触发时，服务端遍历内存中的连接并广播

旧方案涉及的关键点：

- 额外监听端口 `NOTIFICATION_WS_PORT=3001`
- 浏览器连接地址类似 `wss://domain:3001?token=...`
- 服务端在内存里维护连接池

### 旧方案的问题

#### 1. 部署链路不闭合

当前生产入口只有 `web:3000` 通过 `cloudflared` 暴露。  
独立的 `3001` 没有一起暴露，也没有单独代理，所以浏览器无法稳定访问。

#### 2. 浏览器依赖额外公网端口

这和当前“仅通过前端入口对外”的部署目标冲突。  
一旦额外端口未开放，通知能力就直接失效。

#### 3. 文档和环境配置容易混淆

本地开发、容器部署、外部访问三件事混在一起时，`ws://domain:3001` 的解释成本很高，也容易误导。

#### 4. 对当前需求来说有些过度

工单通知是典型的“服务端单向推送”场景：

- 前端不需要通过该连接向服务端发消息
- 不需要复杂双向协商
- 不需要浏览器主动发控制命令

这种场景并不一定要上 WebSocket。

## 新方案：同入口 SSE

### 为什么选 SSE

SSE（Server-Sent Events）本质上是普通 HTTP 长连接响应流：

- 浏览器通过 `EventSource` 发起请求
- 服务端持续返回 `text/event-stream`
- 事件从服务端单向推送到客户端

这正好符合当前项目的通知特征：

- 单向推送
- 同域访问即可
- 能直接复用 `web:3000`
- 能直接穿过 `cloudflared`

### 实现方式

现在的通知链路改成：

1. 前端直接连接 `/api/notifications/stream`
2. 服务端认证当前登录用户
3. 服务端为该用户创建一个 SSE 订阅流
4. 连接建立时先发送一次 `snapshot`
5. 后续工单事件通过内存订阅池广播到 SSE 连接
6. 定时发送 `ping` 保活

### 关键实现点

#### 1. 同入口暴露

通知接口现在挂在 `web` 内部：

- `GET /api/notifications/stream`

不再需要：

- `/api/notifications/session`
- `NOTIFICATION_WS_PORT`
- 独立的 `ws://...:3001`

#### 2. 事件类型

当前 SSE 流使用了三类事件：

- `snapshot`
  - 初次连接时返回当前待办数量
- `ticket`
  - 工单创建、转派、回复、关闭等通知
- `ping`
  - 保活心跳

#### 3. 前端接入

前端改为：

```ts
const eventSource = new EventSource("/api/notifications/stream");
```

而不是：

```ts
const socket = new WebSocket(wsUrl);
```

### 当前事件来源

虽然传输层变了，但业务触发点没有推倒重写，仍然保留在工单服务层：

- 创建工单后广播
- 回复工单后广播
- 转派工单后广播
- 关闭工单后广播

这样做的好处是：

- 业务层改动小
- 事件语义不变
- 只替换了通知传输方式

## WebSocket 与 SSE 对比

| 对比项       | WebSocket                      | SSE                          |
| ------------ | ------------------------------ | ---------------------------- |
| 连接协议     | 独立升级协议                   | 普通 HTTP                    |
| 通信方向     | 双向                           | 服务端单向                   |
| 浏览器接入   | `WebSocket`                    | `EventSource`                |
| 代理兼容性   | 依赖代理对 WS 升级支持         | 通常更容易通过现有 HTTP 代理 |
| 额外端口需求 | 常见于单独服务端口             | 可直接复用现有 HTTP 入口     |
| 实现复杂度   | 较高                           | 较低                         |
| 自动重连     | 需自行处理                     | 浏览器原生支持基本重连       |
| 适用场景     | 聊天、协作编辑、游戏、双向控制 | 通知、进度推送、状态流       |

## 为什么这个项目更适合 SSE

基于当前代码和部署现状，SSE 更合适的原因有四个：

1. 当前通知需求是单向推送，不需要双向实时通信。
2. 现有生产入口只有 `web:3000`，SSE 可以直接复用。
3. `cloudflared` 代理普通 HTTP 流比独立 `ws:3001` 更自然。
4. 浏览器原生 `EventSource` 更省心，减少前端连接治理成本。

## SSE 方案的优点

### 1. 部署简单

不需要额外暴露通知端口，直接走：

- `cloudflared -> web:3000 -> /api/notifications/stream`

### 2. 与当前架构一致

当前项目已经有很多基于 HTTP 的流式能力，例如聊天回答 SSE。  
通知也统一走 HTTP 流，整体更一致。

### 3. 前端实现更轻

前端只需要：

- 建立 `EventSource`
- 监听事件类型
- 更新待办数和站内提醒

不需要额外处理 `wsUrl` 拼接和额外端口。

### 4. 对当前需求足够

工单通知不是实时协作系统。  
只要能稳定收到“新待办”“已转派”“已关闭”，SSE 就已经满足目标。

## SSE 方案的缺点

### 1. 只能服务端单向推送

如果未来要让浏览器通过同一连接主动发命令给服务端，SSE 不适合。

### 2. 仍然是进程内连接池

当前实现虽然换成了 SSE，但连接池仍然在 `web` 进程内存中。  
这意味着：

- 单实例没问题
- 多实例时仍然需要进一步引入跨实例事件总线
- 进程重启后连接会断开并重连

所以这次改造主要解决的是“对外链路不通”和“部署不匹配”，不是分布式扩展问题。

### 3. 长连接仍需要保活

中间代理可能回收空闲连接，因此当前实现里增加了 `ping` 心跳事件。

## 当前实现边界

这次从 WS 切到 SSE，解决的是以下问题：

- 浏览器不再依赖 `:3001`
- 通知可以通过现有 `web:3000` 入口代理
- 前端和部署方式更一致

但以下问题并没有在这次改造里一并解决：

- 多实例下的跨实例广播
- 分布式事件总线
- 通知持久化与离线补偿
- 更复杂的连接状态监控

## 后续建议

如果未来系统继续演进，可以按优先级考虑：

1. 先保持 SSE，不要过早回到 WebSocket
2. 如果进入多实例部署，再引入 Redis Pub/Sub 或消息总线
3. 如果需要通知中心、已读未读、离线补偿，再做通知持久化
4. 只有在出现明确的双向实时交互需求时，再重新评估 WebSocket

## 总结

这次从 WebSocket 改为 SSE，不是为了“技术换技术”，而是为了让通知能力和当前部署方式一致。

简化后得到的结果是：

- 业务事件触发点保留
- 前端连接方式更简单
- 生产代理链路闭合
- 文档和配置解释成本下降

对这个项目当前阶段来说，SSE 是更稳、更符合目标的实现。
